Build from source ​

Tilepress is a desktop app with a React and TypeScript interface (built with Vite) and Python business logic. pywebview opens a native window with the WebView2 runtime built into Windows and lets the interface call Python methods directly. PyInstaller bundles Python, the backend and the built interface into Tilepress.exe, and the WiX Toolset packs that into an MSI.

Tilepress is free software under the GNU GPL, version 3 or later. Before you send a change, read CONTRIBUTING.md.

Prerequisites ​

  • Windows 10 or 11, 64-bit. Several features use Windows itself (Office automation, Windows OCR, face detection, printing).
  • Python 3.11 or later.
  • Node.js 20 or later.
  • The .NET SDK 6 or later, only to build the .msi installer.

Setup ​

Get the code:

powershell
git clone https://github.com/epicabdou/tilepress.git
cd tilepress

Create a virtual environment and install the Python and frontend dependencies:

powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
npm --prefix frontend install

Run in development ​

powershell
.venv\Scripts\python scripts\dev.py

This starts the Vite dev server on 127.0.0.1:5173 and opens the app window pointed at it.

  • React changes reload straight away.
  • After changing Python, close the window and run the command again.
  • DevTools are on in development: right-click and choose Inspect.
  • Closing the window stops Vite.
  • Extra flags are passed to the app, for example scripts\dev.py --self-test.

If you open http://127.0.0.1:5173 in an ordinary browser, you see the interface, but it can't reach Python: the status button says No Python backend.

backend\main.py is the entry point, both from source and in the packaged build. It accepts --dev (load the interface from the Vite server), --debug (turn on DevTools) and --self-test (see Tests).

Build the app ​

powershell
.venv\Scripts\python scripts\build.py

This builds the React app, then runs PyInstaller. The result is dist\Tilepress\Tilepress.exe, a folder build that starts fastest. Zip the dist\Tilepress folder to hand it out. The licence and third-party notices are copied next to the exe.

powershell
.venv\Scripts\python scripts\build.py --onefile

This makes a single dist\Tilepress.exe instead. It's easier to pass around, but it starts more slowly, because it unpacks itself to a temporary folder on every launch.

Build the MSI installer ​

powershell
.venv\Scripts\python scripts\build.py --msi

This builds the folder version, packs it into dist\Tilepress-<version>-x64.msi (about 75 MB), and runs Windows Installer's consistency checks on it. Add --skip-app to repack the existing dist\Tilepress folder without rebuilding it. --msi can't be combined with --onefile.

  • Tooling: WiX Toolset 5.0.2 is pinned in dotnet-tools.json and restored automatically; it needs the .NET SDK. The project stays on WiX 5 because WiX 6 and later require accepting the Open Source Maintenance Fee EULA.
  • Sources: installer\Tilepress.wxs describes the package, files and Start menu shortcut. installer\TilepressUI.wxs has the dialogs: Welcome, Ready to install and Finish, with no licence page.
  • Artwork: the installer images in assets\installer\ and the app icon assets\icon.ico are generated by scripts\make_brand.py. Edit that script and run .venv\Scripts\python scripts\make_brand.py to regenerate them.
  • New version: bump __version__ in backend\toolbox\__init__.py and build again. A newer MSI replaces the installed version; an older one refuses to install over a newer one.

WARNING

Never change the UpgradeCode in installer\Tilepress.wxs. It's how Windows knows a new MSI is an upgrade of the same product. If it changes, versions install side by side.

The installer is per-user by default (%LocalAppData%\Programs\Tilepress, no admin prompt). Run it elevated with ALLUSERS=1 to install for everyone in Program Files. See Getting started for the user's side.

Tests ​

powershell
.venv\Scripts\python -m pytest

The unit tests in backend\tests cover the business logic in backend\toolbox\services.

The tests that start Microsoft Office or LibreOffice are slow, so they're skipped by default. To run them:

powershell
$env:TOOLBOX_OFFICE_TESTS = "1"; .venv\Scripts\python -m pytest backend/tests/test_convert.py

The image AI tests use small stand-in models, to check tiling, masking and the checksum-verified download. To run them with the real models, point TOOLBOX_AI_MODELS at a models folder, such as the app's own:

powershell
$env:TOOLBOX_AI_MODELS = "$env:LOCALAPPDATA\Tilepress\models"; .venv\Scripts\python -m pytest backend/tests/test_images.py

The frontend has a linter:

powershell
npm --prefix frontend run lint

The self-test ​

powershell
dist\Tilepress\Tilepress.exe --self-test

The self-test checks the whole stack, which catches a packaged build that's missing a library or its data files:

  1. It renders a PDF page with PDFium.
  2. It opens the real window and waits until the interface has connected to Python and the Explorer has listed its first folder.
  3. It prints Markdown with code highlighting to PDF through WebView2, converts an image, and loads the Office automation modules (without starting Office).
  4. It runs the PDF tools on a small generated PDF (to Word, PowerPoint, Excel and Markdown, watermark, protect, compress, booklet layout, and a digital signature that it then verifies) and loads the Windows OCR modules. Then it runs the image tools on generated pictures (HEIC, WebP and AVIF, resize, the editor with text and a filter, a watermark, the Windows face detector) and loads ONNX Runtime.
  5. It exits with code 0 on success and 1 on failure.

It works with backend\main.py, scripts\dev.py and packaged builds, so you can use it in CI.

Project layout ​

PathWhat's there
backend\main.pyEntry point, from source and for PyInstaller
backend\toolbox\app.pyCreates the window, picks the dev or built URL, runs --self-test
backend\toolbox\api.pyThe methods the interface can call (window.pywebview.api)
backend\toolbox\paths.pySource vs. packaged paths, and the per-user data folder
backend\toolbox\html_print.pyHTML to PDF and HTML to Image, with WebView2 in a hidden window
backend\toolbox\services\The business logic, with no UI imports and unit-tested: pdf\, convert\, frompdf\, editing\, security\, printing\, images\, latex.py, components.py (the Tectonic download), history.py, settings.py, filesystem.py, preview.py
backend\tests\The tests
frontend\src\lib\bridge.tsTyped wrapper around window.pywebview.api
frontend\src\lib\workspace.tsShared selection and "open this file in tool X"
frontend\src\tools\registry.tsxCategories and tools; the navigation and Find a tool are built from it
frontend\src\browser\, frontend\src\preview\The Explorer and the Preview pane
frontend\src\components\Shared UI: Find a tool, the status panel, History, menus, icons
frontend\src\pdf\, convert\, frompdf\, editing\, security\, print\, latex\, images\The tools, one folder per area
scripts\dev.py, build.py, make_brand.py
installer\The WiX sources for the MSI
assets\The app icon and the installer artwork

The Python package and some internal names (toolbox, the TOOLBOX_* variables, storage keys) keep the app's old name on purpose: renaming them would break saved state. The product name lives in APP_NAME in backend\toolbox\__init__.py and in frontend\src\brand.ts.

Adding a feature ​

  1. Write the logic in backend\toolbox\services\ and add tests.
  2. Expose it as a public method on Api in backend\toolbox\api.py. Return JSON-serialisable values; a raised exception rejects the JavaScript promise with its message. If the method writes files, decorate it with @_records("<tool name>") so its runs appear in the History. Name its source argument path, paths or items and return {path, ...}, {files: [...]} or a list of those, and the inputs and outputs are picked up automatically. Tool options are never recorded.
  3. Add the method's signature to PyApi in frontend\src\lib\bridge.ts.
  4. Call it from React with await call('your_method', arg1, arg2).
  5. For a new screen, add a component and register it under a category in frontend\src\tools\registry.tsx, with an icon and a one-line hint (shown in Find a tool). For a new category, add its id to CategoryId in src\lib\workspace.ts, then add an entry to CATEGORIES with its short tab name and icon.
  6. Style it with the shared classes (card, btn btn-primary / btn-secondary / btn-ghost, text-input, segmented, side-panel, action-bar) and the colour tokens in src\index.css (--glass, --bg-elev, --field, --accent, --accent-grad…), so it works in the light and dark themes. Pop-ups that use position: fixed must be rendered through a portal, as ContextMenu is; inside a frosted panel they would be clipped.
  7. To work with files from the Explorer, read the selected item with useWorkspace().selected, accept "open in this tool" requests with useToolRequest('<tool id>', path => …), and add a matching entry to the file context menu in src\browser\FileBrowser.tsx.

Calls from JavaScript run on pywebview worker threads, so slow work doesn't freeze the window. Show a busy state in the interface while you wait.
